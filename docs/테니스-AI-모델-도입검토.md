# TENNIS LAB 테니스 AI 모델 도입 검토

검토일 2026-11-21. 공개 원문·README·파일 목록에서 확인한 사항과 향후 설계안을 구분했다. 데이터와 가중치의 실제 다운로드·실행 성능은 검증하지 않았다.

**권장 조합은 사용 동의를 받은 자체 스마트폰 포핸드 영상과 기존 MediaPipe 33점, 그리고 소형 시계열 단계 분류기 후보**다. 먼저 현행 휴리스틱을 동일한 라벨에서 측정한다. 공개 자료 중 THETIS는 포핸드 동작 다양성 확인에 가깝고, RacketVision은 공·라켓 분석 확장에 가장 직접적이다. 세 후보에서 준비·백스윙·전방 스윙·팔로스루의 프레임 경계 라벨이나 이를 바로 출력하는 공개 가중치는 확인하지 못했다.

## 2. 현재 코드와 연결

현재 `pose-engine.mjs`는 클립당 최대 30초·50MiB, 12Hz를 기준으로 브라우저에서 MediaPipe CPU 추론을 실행한다. 각 표본에는 시각, 정규화한 2D 관절, 골반 중심 상대 3D 관절이 들어간다. `pose-phases.mjs`는 손목·어깨 신호의 규칙 기반 후보를 만들고, `pose-compare.mjs`는 같은 구간의 상대 진행률을 맞춘다. 단일 카메라 3D 값은 추정값이다. [MediaPipe 출력 명세](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker?tab=Web)

- **THETIS 연결**. 이용 조건 확인 후 RGB에 같은 MediaPipe 설정을 적용한다. 현행 업로더가 MP4만 받으므로 실험실에서는 AVI를 처리할 별도 디코더 또는 오프라인 변환을 사용하고, 원본 시간 정보와 변환 내역을 기록한다. 제공 골격 AVI에는 추정 결과가 영상으로 표현되어 있으므로 그 파일을 33개 수치 배열로 직접 읽을 수 없다. 원시 수치 좌표가 별도로 확인되면 공통 관절 대응표를 정의하고 깊이 센서 좌표계로 구분한다.
- **공·라켓 연결**. 프레임 시각을 기준으로 MediaPipe 시계열과 결합한다. 공 위치와 라켓 키포인트는 별도 채널로 저장하며, 크롭·리사이즈·미러링의 역변환으로 원본 영상 좌표를 맞춘다. 관측 신호의 누락은 마스크로 표시한다. 2D 객체 좌표를 골반 기준 3D 값으로 변환하려면 별도의 깊이 또는 보정 자료가 필요하다.
- **단계 모델 설계 후보**. 어깨·골반·타구측 손목·팔꿈치 좌표와 가시성, 시간차, 몸통 길이로 정규화한 상대 위치와 이동, 추정 3D 축 방향을 입력으로 사용하는 소형 1D 시간 합성곱 모델(TCN)을 첫 학습 후보로 둔다. 준비·백스윙·전방 스윙·팔로스루·기타를 시간축에서 출력하고, 잘린 단계·가림·낮은 확신에는 유보할 수 있게 한다. 기존 규칙기의 보류 이유와 비교해 오류를 진단한다. 분류기와 규칙기는 같은 구간 결과 구조를 반환하며, 브라우저 UI는 자동 후보·수동 수정 출처를 계속 표시한다.

## 4. 길이가 다른 영상의 자동 정렬

1. 각 영상의 실제 프레임 시각을 기반으로 단계 후보의 시작·끝, 출처, 사용 가능한 관절, 경계 불확실 구간을 저장한다. 가변 FPS에서 프레임 번호만으로 초를 계산하지 않는다. 한 영상에 타구가 여러 번 있으면 타구를 고르게 하고, 잘린 구간은 결측으로 남긴다.
2. 양쪽에서 관측되고 순서가 일치하는 같은 이름의 단계만 묶는다. 기존 0–100% 방식처럼 구간 내부 진행률을 각 영상의 실제 시각으로 역변환하고 가장 가까운 유효 관측 시점을 표시한다. 가림을 건너 뛰어 가상의 점을 만들지 않으며 관측 간격이 큰 곳은 비교 보류로 남긴다.
3. **단계 내부 진행률은 상대 위치 표시다.** 같은 진행률이 같은 운동학 이벤트임을 가정하지 않는다. 각 영상의 시작·끝 초와 지속 시간 차이를 별도로 보여준다. 수동 경계와 기준점 방식은 유지한다. 검증 자료가 쌓인 뒤에만 제한적 DTW를 비교 실험하고, 왜곡과 경계 오차가 줄어드는지 확인한다.
4. 비교 결과의 연구용 출력은 원본 시간, 상대 진행률, 신호 가시성, 비교 보류 사유다. 타구측·촬영 각도 차이를 검토하며, 자세 점수나 이상적인 관절 각도는 제공하지 않는다.

## 5. 브라우저·서버 실행과 자원

| 방식 | 장점 | 조건과 한계 |
| --- | --- | --- |
| **브라우저 우선** | 영상 서버 업로드가 없고 현행 HTML·JS 및 2D/3D UI에 연결하기 쉽다. 소형 단계 분류는 좌표만 처리한다. | Web Worker에서 기존 MediaPipe 처리와 비교하고, 필요시 ONNX Runtime Web의 WASM·WebGPU를 검토한다. WebGPU에서 모델 연산자가 지원되는지 확인한다. 대형 .pth 체크포인트는 브라우저에서 그대로 사용할 수 없으며, 추후 변환 후 정확도와 기기 메모리를 재측정한다. |
| **별도 추론 서버** | 검증된 Python·PyTorch·CUDA 환경으로 RacketVision을 실험하기 쉽고 실행 환경을 통제할 수 있다. | 서버 비용과 전송·보관 부담이 늘어난다. 원본을 보내는 서비스는 현재 브라우저 전용 흐름과 별도 설계·동의가 필요하다. 초기 비교는 로컬 연구용 실행을 우선하며 현재 Vercel API에 GPU 추론을 추가하지 않는다. |

Vercel Hobby는 정적 프론트와 Node 조회 API를 계속 담당한다. 공식 Fluid Compute 문서 기준 Hobby 함수는 **2GB·1 vCPU**, 요청 본문 **4.5MB** 제한이다. 현행 50MiB 영상 입력과 PyTorch·CUDA 연구 파이프라인을 그대로 함수에 올리는 구성은 적합하지 않다. Hobby의 개인·비상업적 조건과 월 전송량을 확인하고 공개 모델을 직접 배포하는 경우 최초 다운로드 및 캐시 적중률을 비용에 계산한다. 오픈 파일은 무료 호스팅·GPU 실행 한도를 의미하지 않는다. [ONNX Runtime Web](https://onnxruntime.ai/docs/tutorials/web/) · [Vercel 함수 한도](https://vercel.com/docs/functions/limitations) · [Vercel Hobby](https://vercel.com/docs/plans/hobby)

공개 체크포인트 용량은 디스크 크기다. 모델의 실행 RAM·VRAM과 스마트폰 응답 시간은 미측정이다. RacketVision 공식 설치 안내는 PyTorch·CUDA 환경을 제시하고 라켓 모듈에는 MMDetection·MMPose가 추가된다. 실제 도입 전 모델 단독과 MediaPipe·디코더 동시 실행에서 최고 메모리, 첫 실행과 재실행 시간, 브라우저 초기 다운로드, Fallback 실패율을 기록한다. 예를 들어 640×360 RGB 3프레임의 float32 입력은 약 7.9MiB지만, 활성값·가중치·영상 프레임 버퍼는 별도다. 수치 예시는 모델의 총 메모리 요구량이 아니다. [공식 환경 설정](https://github.com/OrcustD/RacketVision#2-environment-setup)

## 6. 검증용 정답 라벨 설계

- **수집**. 먼저 실패한 A·B 사례를 포함하되 이용 동의를 받은 파일만 사용한다. 고정 측면·사선·후면, 좌우 타구 손, 스탠스와 숙련도, 촬영 FPS, 가림·화면 잘림·배경 타구를 고르게 포함한다. 정지, 연습 스윙, 포핸드가 아닌 타구도 음성 예제로 둔다. 선수·촬영 세션 단위로 학습·검증·최종 테스트를 나눈다. 같은 원본의 크롭과 재인코딩은 같은 분할에 둔다.
- **라벨 원칙**. 두 평가자가 자동 후보를 보지 않고 원본 프레임 시각에서 독립적으로 표시한다. 준비 시작은 첫 명확한 준비 동작, 백스윙 시작은 라켓 또는 타구 팔의 지속적인 테이크백 시작, 전방 스윙 시작은 타구 방향으로 이어지는 지속적인 전환, 팔로스루 시작은 전방 가속이 끝난 뒤 이어지는 감속·휘감기, 종료는 후속 동작으로 전환하는 시점으로 초안을 둔다. 제품 라벨 정의는 코치와 파일럿에서 합의한다. 접촉 라벨은 별도이며 팔로스루 시작 시각과 강제로 동일하게 두지 않는다.
- **저장할 필드**. 익명 영상·타구 ID, 원본 FPS 정보와 표시 시각, 타구 손·카메라·스탠스, 경계별 허용 시간 범위, 평가자 ID, 가림·잘림·불확실 사유, 라벨 지침 버전을 기록한다. 중재 결과와 최초 판단을 함께 남긴다. 독립 판단이 어려운 구간은 빈 값으로 둔다.
- **검증 지표**. 경계별 절대오차(ms) 중앙값 및 상위 분위수, 단계별 구간 겹침, 후보를 낸 비율·오탐·보류율과 평가자 간 편차를 함께 본다. 후보가 없는 영상도 집계에 포함한다. 관절 표시율과 단계 검증 성능은 별도다. 촬영 각도·FPS·타구 손·가림별 결과를 나누고, 기준값은 파일럿 이후 사전 합의한 절차로 정한다.

## 7. 도입 순서

1. **현행 재현과 라벨 파일럿**. 기존 자동 후보·수동 경계 진단으로 A·B와 음성 사례를 기록한다. 평가자 간 일치가 낮은 경계는 라벨 정의부터 수정한다.
2. **포즈 기반 단계 분류 비교**. 승인된 데이터로 소형 TCN을 실험하고 동일한 홀드아웃에서 현재 규칙기와 비교한다. 검증된 경우에만 브라우저 후보 제공자로 추가하고, 수동 입력을 유지한다. THETIS는 권리를 확인한 뒤 포핸드 종류 보조 실험에만 사용한다.
3. **객체 추적 실험**. RacketVision 테니스 일부와 별도 스마트폰 라벨로 공 추적 및 라켓 키포인트를 각각 검증한다. 비공식 TrackNet은 접근성과 권리를 확인한 뒤 공 추적 비교군으로 검토한다. 실험 단위로 체크포인트의 권리와 안전한 형식을 확인한다.
4. **임팩트·래깅 검증 후 확장**. 객체 추적 오차와 실제 이벤트 오차를 따로 측정한다. 확인되지 않는 영상에서 유보하고, 단계 모델로 얻은 후보를 정밀 이벤트의 근거로 사용하지 않는다.

이번 작업은 문서만 추가했다. 모델 설치·대용량 다운로드·학습·배포·DB 변경은 수행하지 않았다.

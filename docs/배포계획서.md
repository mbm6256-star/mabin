# TENNIS LAB 배포 계획서

검토일: 2026-11-21. 수업 공개용 첫 배포는 **Vercel Hobby + Supabase Free**를 권장한다. 비상업적 개인 프로젝트라는 조건과 아래의 보안·사용량 확인이 전제다. 이 문서는 배포 전 계획이며 배포, 계정 변경, 유료 기능 활성화는 수행하지 않았다. 가격은 세금과 환율을 제외한 USD 기준이다.

데이터 흐름은 **브라우저 → Vercel 정적 화면·조회 API → Supabase DB**다. 영상은 **기기 파일 → 브라우저 MediaPipe·Three.js → 화면**으로 흐른다. 모델·라이브러리 다운로드는 외부 자산 서버 요청으로 별도 집계한다.

GitHub 원격 `main`과 로컬 `HEAD`는 모두 `ef7ce75`다. 계획서 작성 전 로컬에는 수정 5개와 미추적 파일 11개가 있었다. 최신 분석 코드와 테스트는 아직 원격 커밋에 포함되지 않았다.

## 3. 분석 1회 측정 방법

**분석 1회**는 MP4 한 편의 분석 시작부터 결과 표시까지다. A/B 1회는 두 편을 순서대로 분석하므로 영상 분석 2회로 집계한다. 실제 시간·메모리·네트워크 바이트는 이번 계획에서 측정하지 않았다. 코드에서 확인한 한도는 영상당 **30초·50MiB**, 초당 **12개 표본**, 최대 **360개 표본**이다. 두 파일 합계 최대 100MiB는 입력 파일 크기이며, 디코딩 버퍼나 모델을 포함한 메모리 한도가 아니다.

| 무엇을 측정하나 | 측정 방법 |
| --- | --- |
| 걸린 시간 | 같은 MP4로 모델 다운로드를 포함한 첫 실행과 캐시가 있는 재실행을 나눈다. 브라우저 개발자 도구 Performance에서 클릭부터 결과 표시까지 기록하고, 모델·WASM 로딩, 프레임 읽기·추론, 3D 초기화를 구분한다. 데스크톱과 스마트폰에서 5회 이상 반복해 중앙값과 최댓값을 남긴다. |
| 메모리 | 브라우저 작업 관리자에서 빈 화면, 파일 선택, 분석 중 최고점, 결과 화면, 파일 교체 후를 비교한다. JS Heap은 Memory 도구에서 따로 기록한다. 프로세스 메모리에는 영상 디코더·WASM 등의 영향이 있고 JS Heap만으로는 전체를 설명할 수 없다. 단일과 A/B를 각각 측정한다. |
| CPU와 GPU | Performance에서 추론 중 CPU 활동과 메인 스레드 지연을 확인한다. CPU 초는 경과 시간과 별도로 기록한다. 브라우저·OS 작업 관리자에서 GPU를 관찰하고 3D 뷰어를 열기 전후의 차이를 본다. 영상 디코딩과 렌더링도 GPU 사용에 포함될 수 있다. |
| 저장공간 | MP4 파일 크기와 브라우저 캐시·로컬 저장 사용량을 분리한다. Supabase 대시보드에서 기존 DB 크기와 월 송신량을 확인한다. 영상 분석 전후 서버 Storage에 영상이 생기지 않는지 확인한다. |
| 외부 호출과 전송량 | Network에서 호스트별 요청 건수와 전송 크기를 기록한다. jsDelivr·Google 모델 자산, Vercel 자체 API, Supabase 송신을 각각 집계한다. Supabase 호출은 서버에서 발생하므로 대시보드 또는 값이 제거된 서버 로그에서 확인한다. 캐시를 끈 첫 방문과 일반 재방문을 분리하고, 네트워크 기록 공유 시 인증 헤더와 사용자 데이터를 제거한다. |

## 4. 월간 사용량과 비용 예시

아래 수치는 계산 예시다. **한 방문에 영상 한 편**, 10초 분량(120표본), 브라우저 처리 경과 20초와 활성 CPU 8초, 기기별 분석 중 추가 메모리 피크 150MiB를 가정한다. 메모리 피크는 동시 작업의 부담이며 월 횟수에 곱해 저장량으로 계산하지 않는다. GPU 시간은 기기별 실측 후 산정한다.

한 방문에 config·선수·경기 API 각 1회, Supabase 조회는 최소 한 페이지씩 총 3회라고 가정한다. 현재 경기 조회도 선수 조회를 선행하므로 선수 2회와 경기 1회다. 페이지 추가, 새로고침, 실패 재시도, 영상 없는 방문은 별도로 늘어난다. 방문당 Vercel 총 송신 1MB, 그중 별도 집계하는 Origin 전송 0.3MB, Supabase 일반 송신 0.25MB, 첫 방문 기준 외부 자산 요청 7건·10MB를 예시로 가정한다. 함수당 활성 CPU 20ms와 실행 0.3초·할당 1GB도 가정이다. 이 수치들은 현재 프로젝트나 요금제의 실측값이 아니다.

| 월 영상 분석 | 기기 총 경과 / CPU 시간 합계 | Vercel 호출 / 활성 CPU / 메모리 시간 | Vercel 송신 / Origin | Supabase 조회 / 일반 송신 | 외부 자산 요청 / 전송 (전부 캐시 없음 가정) | 월 요금 예시 |
| --- | --- | --- | --- | --- | --- | --- |
| 100회 | 0.56시간 / 0.22 CPU시간 | 300회 / 0.0017 CPU시간 / 0.025GB·시간 | 0.10GB / 0.03GB | 300회 / 0.025GB | 700회 / 1GB | 조건 충족 시 $0 |
| 1,000회 | 5.56시간 / 2.22 CPU시간 | 3,000회 / 0.0167 CPU시간 / 0.25GB·시간 | 1GB / 0.30GB | 3,000회 / 0.25GB | 7,000회 / 10GB | 조건 충족 시 $0 |
| 10,000회 | 55.56시간 / 22.22 CPU시간 | 30,000회 / 0.167 CPU시간 / 2.50GB·시간 | 10GB / 3GB | 30,000회 / 2.50GB | 70,000회 / 100GB | 조건 충족 시 $0 |

기기 시간은 이용자 전체의 합계다. 외부 자산 전송은 현재 구성에서 Vercel·Supabase 송신에 포함되지 않으며, CDN 장애·속도 제한·캐시 미사용은 분석에 영향을 줄 수 있다. 직접 자산을 호스팅하게 되면 그 전송량을 호스팅 비용에 합산한다. **한 방문당 Supabase 송신이 0.60MB로 커지면 10,000번 방문에서 약 6GB**로 Free 일반 송신량을 넘는다. 따라서 월 분석 횟수만으로 무료 범위를 보장할 수 없다. 경기가 누적되면 실제 응답 크기와 추가 페이지 수를 다시 측정한다.

## 5. 보안 및 GitHub 공개 전 점검

- **키 교체**. 노출 이력이 있는 Secret Key는 새 서버 전용 키로 교체하고, 연결 확인 후 기존 키를 폐기한다. 악용이 진행 중이라면 기존 키를 먼저 폐기한다. 레거시 service_role이 노출된 경우 의존성을 확인하고 공식 절차로 교체·비활성화한다. 키는 Supabase와 Vercel 대시보드에서 관리하고 화면 캡처·채팅·로그에 포함하지 않는다. [Supabase 공식 교체 절차](https://supabase.com/docs/guides/security/rotate-leaked-api-keys)
- **공개 범위**. 현재 선수 조회에는 이름과 `memberCode`가 들어 있다. 공개용 API와 화면에서 불필요한 회원 코드를 제외하고, 선수 이름과 경기 정보의 공개가 허용되는지 확인한다. 허용이 모호하면 수업용 공개 데이터로 준비하거나 접근 제한을 먼저 정한다. 읽기 전용도 인터넷에서 요청할 수 있으므로 공개 응답 필드를 제한한다.
- **권한**. 첫 공개에서 `/api/config`는 저장 비활성 상태를 반환하고, 비인증 `POST /api/matches`는 Supabase 호출 전에 403 또는 405로 막는다. 개발용 저장 플래그를 배포 환경에 설정하지 않는다. 이후 저장을 공개할 때는 서버에서 로그인과 관리자 권한을 확인하고, 실패 시 DB 호출을 하지 않도록 별도 검증한다. Origin·CSRF 확인은 관리자 인증을 대신할 수 없다.
- **비밀 분리**. `.env`·`.env.local`은 Git 무시 대상이고 추적 중인 환경 파일은 `.env.example`뿐이다. 공개 자산 폴더에는 HTML·CSS·JS·MJS만 필요한 목록대로 복사한다. `.env*`, `.git`, SQL, 테스트, 내부 문서는 공개 출력에 넣지 않는다. Vercel 환경 변수 `SUPABASE_URL`과 `SUPABASE_SECRET_KEY`는 서버 함수에서 읽는다. 서버 Secret Key가 RLS를 우회하는 만큼 함수에서 공개 응답을 제한한다. [Vercel 환경 변수](https://vercel.com/docs/environment-variables) · [Supabase 키 권한](https://supabase.com/docs/guides/getting-started/api-keys)
- **GitHub 검수**. 최신 로컬 변경을 커밋하기 전에 스테이징 목록과 Git 이력의 키 패턴을 값 출력 없이 검사한다. 환경 파일에 새 키가 남더라도 추적되지 않는지 확인한다. 분석 모듈이 빠지면 최신 화면에서 로딩 오류가 날 수 있으므로 배포 대상 파일 목록에 포함한다. GitHub 연동은 푸시로 자동 배포가 시작될 수 있어 수동 Preview 흐름을 먼저 확인한다. [Vercel GitHub 연동](https://vercel.com/docs/git/vercel-for-github)

## 6. 배포 순서와 공개 후 체크리스트

1. 노출된 키를 교체·폐기하고 공개 데이터 범위를 확정한다.
2. 로컬 미리보기는 유지하면서 배포용 읽기 API와 정적 자산 목록을 만든다. 로컬 자동 테스트로 API 응답, 저장 차단, 포즈 모듈 경로를 확인한다.
3. 사용자가 배포를 승인한 뒤 Vercel Hobby 프로젝트에 서버 환경 변수를 설정한다. CLI로 **Preview**를 먼저 배포하고 아래 항목을 검수한다. 공개 승인을 받은 뒤 Production을 배포한다. 이후 변경도 Preview에서 먼저 검수한다. [Vercel CLI](https://vercel.com/docs/cli/deploy)
4. 공개 후 사용량 대시보드를 확인하고, Vercel 또는 Supabase 한도의 절반에 이르면 응답 바이트와 호출량을 다시 측정한다. 발표 전에는 Free DB가 활성 상태인지 확인한다.

- [ ] HTTPS에서 홈·선수·경기·랭킹이 열린다. 조회 응답에 불필요한 회원 코드가 없다.
- [ ] `GET /api/players`와 `GET /api/matches`가 정상 동작한다. 환경 설정 오류는 키를 드러내지 않는 오류로 표시된다.
- [ ] 공개 URL에서 비인증 경기 저장이 403/405이고 DB에 새 행이 생기지 않는다. 화면 저장도 비활성이다.
- [ ] `/.env`, `/.git/config`, 서버 소스 및 비공개 파일이 다운로드되지 않는다. 브라우저 번들과 Network에 Secret Key가 없다.
- [ ] PC·스마트폰에서 실제 MP4의 2D·3D·각도·리포트와 A/B 기준점·구간 비교를 확인한다. 잘못된 MP4, 모델 로딩 실패, 가려진 관절도 확인한다.
- [ ] 분석 중 Network에서 원본 파일 업로드가 없고, Supabase Storage와 호스팅 저장소에 영상이 생기지 않는다.
- [ ] 첫 로딩과 재방문 성능, API 응답 크기, 송신량을 기록한다. 무료 한도 접근 시 비용 승인 없이 유료로 전환하지 않는다.

**다음 작업 한 가지** — Supabase 대시보드에서 이미 노출된 Secret Key를 새 서버 전용 키로 교체하고 기존 키를 폐기한다.

# 프론트엔드 API 연결 확인

서버가 실행 중인 상태에서 http://127.0.0.1:4173 에 접속합니다.
HTML 파일을 직접 열거나 다른 정적 서버를 사용하면 API를 조회할 수 없습니다.
HTML/CSS는 즉시 반영되지만 경기 POST API와 환경변수 변경은 서버 재시작이 필요합니다.
개발용 경기 저장은 [경기저장-개발테스트.md](./경기저장-개발테스트.md)를 참고하세요.

## 실제 DB 데이터 확인

1. 홈에서 DB 선수 4명, DB 경기 5건, 최근 경기 3건을 확인합니다.
2. 경기 기록 화면에서 5경기와 각 경기의 두 세트 점수를 확인합니다.
3. 랭킹을 확인합니다. 현재 데이터 기준 박지우(p3)는 3경기 2승 1패,
   승률 66.7%로 1위입니다. 김하늘(p1)은 4경기 2승 2패 50.0%로 2위,
   이서준(p2)은 3경기 1승 2패 33.3%로 3위입니다.
   최유진(p4)은 미경기이며 순위와 승률은 미경기/—로 표시합니다.
4. 개인 대시보드에서 선수를 바꾸어 경기 수, 승패, 승률과 이력을 확인합니다.
5. 브라우저 개발자 도구의 Network 탭을 열고 새로고침합니다.
   `/api/players`, `/api/matches`가 다시 호출되고 HTTP 200 및
   `X-Data-Source: supabase`를 반환하는지 확인합니다.
   화면의 `DB 새로 조회` 버튼도 같은 두 API를 다시 호출합니다.
6. 브라우저가 Supabase 도메인이나 sample-data.json에 직접 요청하지 않는지 확인합니다.

## 데이터 출처와 저장 안내

- 이전 `tennis-lab-prototype-v1`의 선수·경기는 읽거나 삭제하지 않습니다.
- 경기 등록은 기본 조회 전용이며 로컬 개발용 쓰기 활성화 시에만 사용할 수 있습니다.
  선수 등록 폼은 계속 비활성화 상태입니다.
- 영상 분석의 고정 데모는 유지합니다. 데모 리포트만
  `tennis-lab-demo-reports-v2`에 저장하며 DB 기록·랭킹에는 영향을 주지 않습니다.
- 데모 리포트 초기화는 해당 브라우저의 리포트만 지우고 DB에는 요청하지 않습니다.

## 로딩·실패·빈 결과·모바일

- Network 속도를 느리게 설정한 뒤 새로고침하여 로딩 안내를 확인합니다.
- 개발자 도구에서 `/api/matches`를 요청 차단한 뒤 DB 새로 조회를 누릅니다.
  조회 실패 안내가 나타나고 이전 DB 화면이나 샘플이 대신 표시되지 않아야 합니다.
  차단을 해제하고 다시 불러오기로 복구합니다.
- 빈 DB는 안내와 0건을 표시합니다. 실제 DB 데이터를 삭제해서 시험하지 마세요.
  아래 자동 브라우저 테스트는 API 응답을 브라우저 안에서만 모의 처리해
  빈 데이터·HTTP 오류·잘못된 출처·복구 상태를 확인합니다.
- 모바일 에뮬레이션 390px에서 다섯 화면을 확인합니다. 테이블 내부 가로 스크롤은
  유지하며 페이지 전체에 불필요한 가로 스크롤이 없어야 합니다.

## 자동 테스트

```powershell
node --check app.js
node --test core.test.cjs preview.test.mjs
node frontend.browser.test.mjs
```

브라우저 테스트는 실행 중인 4173 서버와 Windows Edge를 사용합니다.
다른 Chromium 브라우저는 `BROWSER_EXECUTABLE` 환경변수로 경로를 지정할 수 있습니다.
테스트 전용 임시 프로필을 사용하므로 일반 브라우저의 저장 내용은 변경하지 않습니다.
실제 DB에 요청하는 작업은 GET 조회뿐입니다. 오류/빈 응답은 브라우저에서 가로챕니다.
Secret Key는 프론트엔드나 테스트 코드에 넣지 않습니다.

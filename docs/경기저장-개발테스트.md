# 경기 저장 및 랭킹 갱신 — 로컬 개발 전용

이 기능은 관리자 로그인을 구현한 운영 서비스가 아닙니다. 서버는 127.0.0.1에만
바인딩하며, 개발 환경변수 두 개를 명시적으로 설정해야 저장할 수 있습니다.
선수 등록·경기 수정·삭제 API는 추가하지 않았습니다.

## 1. Supabase 저장 함수 설치 (사용자가 직접 실행)

`supabase/save_match.sql` 전체를 Supabase SQL Editor에서 실행합니다.
이 SQL은 저장 함수와 그 함수의 실행 권한만 설정합니다. 기존 테이블·컬럼·RLS·
경기 데이터는 변경하지 않으며 테스트 경기도 추가하지 않습니다.
함수는 SECURITY INVOKER이며 PUBLIC/anon/authenticated 실행을 차단하고
service_role만 실행할 수 있습니다. 서버 Secret Key는 RLS를 우회하는 역할이므로
로그인·운영자 권한 검증을 대신하지 않습니다.

설치 확인용 조회:

```sql
SELECT to_regprocedure('public.save_tennis_match(text,text,date,jsonb)');
SELECT role_name,
       has_function_privilege(
         role_name,
         'public.save_tennis_match(text,text,date,jsonb)',
         'EXECUTE'
       ) AS can_execute
FROM (VALUES ('anon'),('authenticated'),('service_role')) AS r(role_name);
```

정상 권한은 anon=false, authenticated=false, service_role=true입니다.
함수가 없으면 POST는 `503 SAVE_FUNCTION_NOT_INSTALLED`로 안내합니다.
Data API의 함수 캐시 반영이 지연될 수 있으므로 반영 후 다시 확인합니다.

## 2. 개발용 쓰기 활성화

기존 `.env`의 URL과 Secret Key는 그대로 두고 아래 항목을 설정합니다.
키를 채팅·프론트엔드·로그에 넣지 마세요.

```dotenv
NODE_ENV=development
ENABLE_DEV_MATCH_WRITES=true
```

기존 TENNIS LAB 서버를 종료한 뒤 프로젝트 폴더에서 다시 실행합니다.

```powershell
node preview.mjs
```

반드시 http://127.0.0.1:4173 에 접속합니다. localhost 별칭, 프록시 경유,
외부 출처 요청은 저장용으로 허용하지 않습니다.
GET `/api/config`가 활성 여부와 서버 수명 동안의 임의 요청 보호 토큰을 제공합니다.
이 토큰은 Supabase 키가 아니며 관리자 인증 수단도 아닙니다.
POST는 동일 Origin/Host, 실제 loopback 연결, 토큰, JSON 본문(8KB 이하)을 검사합니다.
Forwarded/X-Forwarded-* 헤더가 있으면 차단합니다. Origin 없는 POST도 차단합니다.
기존 서버를 로컬 프록시나 터널로 공개하지 마세요.

배포 환경에서는 `NODE_ENV=production`, `ENABLE_DEV_MATCH_WRITES=false`를 사용합니다.
production에서는 enable 플래그가 true여도 저장하지 않습니다.
두 설정이 누락되어도 기본값은 저장 차단입니다. GET 조회와 포핸드 데모는 유지합니다.

## 3. API 계약

```http
POST /api/matches
Content-Type: application/json
Origin: http://127.0.0.1:4173
X-CSRF-Token: (같은 서버의 /api/config에서 받은 값)
```

```json
{"a":"p4","b":"p1","date":"2026-11-15","sets":[[6,4],[6,3]]}
```

ID와 winner_id는 요청에 포함하지 않습니다. 서버는 선수와 날짜·세트를 검증하고,
DB 함수가 승자를 계산해 경기와 세트를 한 트랜잭션으로 저장합니다.
서버는 반환된 점수·승자를 다시 검증합니다.

- 201: 신규 저장. `{created:true, winner_id, match:{id,date,a,b,sets}}`
- 200: 동일 경기 재요청. `{created:false, winner_id, match:{id,date,a,b,sets}}`
- 400: 잘못된 JSON·선수·날짜·점수 또는 불필요한 필드
- 403: 개발용 저장 제한, 출처 또는 요청 토큰 검사 실패
- 408/413/415: 요청 수신 시간 초과 / 8KB 초과 / JSON 외 콘텐츠
- 409: 이미 존재하는 기록의 충돌·중복 상태 또는 승자 불일치
- 503: 설정·함수 누락 또는 잠금 대기 등 재시도 가능한 DB 오류
- 502: DB 요청 실패 또는 저장 결과 확인 불가

`SAVE_OUTCOME_UNKNOWN`은 저장되지 않았다는 뜻이 아닙니다. 응답이 유실되었을 수
있으므로 DB 조회로 먼저 확인합니다. 자동으로 새로운 경기를 재전송하지 않습니다.

## 4. 중복 정책과 트랜잭션

날짜 + 선수 쌍 + 순서대로 나열한 전체 세트 점수로 동일 경기를 식별합니다.
A/B를 바꾸면서 점수도 뒤집으면 동일 경기입니다. 동일 입력의 재시도는 기존
경기를 반환하고 덮어쓰지 않습니다. 같은 날 같은 선수의 다른 점수는 별도 경기입니다.
동일한 점수의 실제 재대결을 구분하려면 향후 별도 경기 식별 정책이 필요합니다.

DB 함수는 정규화된 경기 식별값에 transaction advisory lock을 잡고,
READ COMMITTED의 새 snapshot에서 중복을 확인한 뒤 저장합니다.
세트 INSERT 실패 시 경기 INSERT도 롤백됩니다. 함수 경로를 거치는 동시 요청과
서버 재시작 후 재요청에 적용되며, SQL Editor 등 다른 경로의 직접 INSERT를
전역적으로 제한하는 UNIQUE 제약을 추가한 것은 아닙니다.

## 5. 안전한 자동 테스트 — 실제 DB에 쓰지 않음

```powershell
node --test core.test.cjs preview.test.mjs preview.write.test.mjs
$env:TENNIS_LAB_BROWSER_MOCK_WRITES = 'true'
node frontend.browser.test.mjs
Remove-Item Env:TENNIS_LAB_BROWSER_MOCK_WRITES
```

브라우저 모의 저장 모드는 임시 포트의 별도 Node 서버와 가짜 Supabase 응답을
사용합니다. 실제 Supabase의 키·URL을 사용하거나 POST하지 않습니다.
중복 클릭·A/B 반전·실패 입력 보존·응답 유실·저장 후 조회 실패·랭킹 갱신·
포핸드 데모·모바일 화면을 검사합니다. 기본 브라우저 테스트 모드는 실제 4173
서버를 조회만 하며 POST를 보내지 않습니다. 기본 모드는 쓰기 비활성 상태를 기대합니다.

SQL 함수 자체는 선택적 PGlite(PostgreSQL WASM) 엔진으로 검증할 수 있습니다.
예를 들어 별도 임시 폴더에 `npm install --prefix <임시폴더> --no-save --no-package-lock
@electric-sql/pglite`를 실행한 뒤 다음과 같이 지정합니다.

```powershell
$env:PGLITE_MODULE = '<임시폴더>\node_modules\@electric-sql\pglite\dist\index.js'
node --test supabase/save_match.test.mjs
Remove-Item Env:PGLITE_MODULE
```

메모리 DB에만 테이블과 테스트 데이터를 생성합니다. 원본 5경기·10세트,
재실행·A/B 반전, 잘못된 입력, 강제로 발생시킨 세트 저장 실패의 롤백,
함수 권한·RLS 유지, Node POST와 SQL 함수의 통합 및 서버 재시작 후 중복 방지를
검증합니다. PGlite는 한 연결에서 직렬 실행하므로 실제 여러 PostgreSQL 세션의
잠금 대기 동작은 별도 통합 환경에서 확인할 항목입니다. 엔진이 없으면 SQL 테스트는 skip됩니다.

## 6. 사용자 수동 저장 테스트 — 실제로 저장됨

이 절차는 실제 DB에 새 경기를 남깁니다. 저장할 경기 정보를 직접 선택한 경우에만 실행하세요.

1. 함수 설치와 개발 환경변수 설정 후 서버를 재시작합니다.
2. 경기 기록 화면에서 개발용 DB 저장 안내와 활성화된 폼을 확인합니다.
3. 선수 2명·날짜·세트 점수를 입력하고 예상 승자를 확인합니다.
4. 저장을 한 번 클릭합니다. 저장 중에는 폼과 새로 조회가 비활성화됩니다.
5. Network에서 POST 201 뒤 두 GET 200을 확인하고 경기·랭킹·개인 통계를 확인합니다.
6. 같은 입력을 다시 제출하면 POST 200이고 경기·세트 건수는 추가되지 않아야 합니다.
7. 새로고침 후에도 DB에서 조회된 기록과 순위가 유지되는지 확인합니다.
8. 잘못된 점수·동일 선수는 저장하지 않아야 합니다.
9. 저장이 성공했지만 재조회만 실패하면 별도 안내가 나타납니다.
   `저장 결과 다시 조회`는 GET만 수행하며 POST를 재전송하지 않습니다.
10. 실습 후 `ENABLE_DEV_MATCH_WRITES=false`로 되돌리고 서버를 재시작해 차단을 확인합니다.

기존 DB 데이터를 지우는 테스트 정리 SQL은 제공하지 않습니다.
